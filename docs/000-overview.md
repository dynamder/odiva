# 000 总览

odiva 是一个常驻桌面的助手，由三面组成：

| 面 | 是什么 | 状态 |
| --- | --- | --- |
| 对话面 | 一个普通的聊天窗口（iced，原生，见 [002](002-ui.md)） | 已实现，接上 core |
| 形象面 | Live2D，独立进程里的透明置顶窗口（wry） | 未开始 |
| 执行面 | N 个 ACP harness 子进程，各自的工作区（见 [005](005-execution.md)） | 进程与台账已有，按新模型重写中 |

中间是**这个助手本人**：读对话、决定派活、决定说什么。不是"人格层"，也不是"调度层"，没有第二个模型替它说话。

她是一个常驻 actor：一个状态机（Idle / Busy）、一组上下文线、一张工具表。线是记录，进程可以丢；
磁盘上的台账与转录是"她"唯一的连续性。模型在需要时被唤醒，不需要时睡着（见 [007](007-core.md)）。

```
odiva (iced, 原生窗口)          stage (wry, Live2D, 透明置顶)
        │ UiMessage / CoreMessage        ▲ 单向指令
        ▼                                │
   odiva-core ───────────────────────────┘
   ├── Odiva actor（状态机、上下文线、工具、提问）
   ├── Ledger actor（tasks/*.json）
   ├── odiva-harness（ACP 会话、Run、提权）
   └── md 记忆 + tantivy 索引（见 004）
```

## 三条不变量

1. **界面上没有工作流词汇。** UI 只认识消息，和一种阻塞式提问卡。没有 task、没有 status、没有进度、
   没有 harness 名字——不是隐藏了，是没有这个概念可以画。说多少、什么时候说，是她的决定，
   在消息到达窗口之前就做完了。
2. **线是记录，进程可丢弃，台账在磁盘。** ACP 的 `end_turn` 只代表"这一轮说完了"；harness 会崩、
   会换、会续不上。任务的真相在 `tasks/<id>.json`，进程只是当下的一次尝试。
3. **记忆是 md，索引可重建。** `journal/` 是流水，`facts/` 是蒸馏，`index/` 随时可以删了重来。

第一条现在仍是构造性质：`say` 是唯一的说话出口，提权与暂停的唯一答复入口是那张提问卡——
两者都不携带工作流词汇，窗口因此没有可画的任务模型。

## Crate 结构

```
crates/
├── odiva-proto/    the seam：消息、在场、一张提问卡、`CoreHandle`。无依赖
├── odiva-harness/  ACP：进程、会话、Run、提权请求。唯一碰 ACP 类型的地方
├── odiva/          聊天窗口（iced）。不持有真值，只有布局
├── odiva-core/     核心：Odiva actor、上下文线、台账、工具
└── ericed/         vendor 自 ../sofaia：widgets、palette、windowed list
```

`odiva-proto` 单独成 crate 的理由只有一条：让契约不可能悄悄引用 core 或 iced 的类型——用编译边界代替约定。
`odiva-harness` 单独成 crate 的理由类似：ACP 的类型与进程细节不该渗进状态机。

## 为什么这么切

- **聊天界面必须原生。** 跑在本地的工具不需要一个浏览器内核来画几行字；webview 的代价是进程外合成、
  IPC 边界、透明窗口的老坑，以及每个功能都要过一遍 JS。
- **Live2D 例外，用 webview。** Cubism 生态事实上围绕 Web 建立，而它只占屏幕一角，且是"单向显示设备"。
- **ericed 是现成的**：虚拟化列表、绘制期变换、手势→意图的词表。它"加一个变体就编译失败"的性质，
  正好用来守 agent 事件与 UI 意图之间的边界。
- **ACP 是执行层的唯一接口。** 原生支持与 adapter 已覆盖主流 harness；提权请求天然上行到 client；
  MCP 可以按需透传进某个 session（我们只透传，不消费）。但**不押注 ACP 的编排能力**——它没有，
  依赖、并发、重试、续会话全靠探测与判断。
- **odiva 不走 ACP。** 它在进程内，直接收用户消息；harness 才是跨进程的那一层。少一层 ACP
  就少一次序列化和一次模型上下文的重复。

## 借了 dsh-superagent 什么

形状是同一个：常驻的统筹者收消息、按工作区分派、多个上下文隔离的 worker 在独立目录干活、干完回来交付。
必须偏离的有两处：

1. **我们不比轨迹详细度。** 想看完整轨迹，dsh 永远更详细更准。odiva 交付的是**判断**——
   "拆成六件，五件在跑，其中两件要改同一个 crate 所以串行"这句话，dsh 不会说。
2. **我们的子单元是外部进程。** harness 有自己的 cwd、模型、权限和独立的死亡方式；它们之间没有共享上下文，
   交接只能靠 brief 与文件。所以 brief 必须自包含，回报必须结构化。

由此推出一条硬结论：**台账以磁盘为准，她的记忆只是缓存。** 重启后不能指望她"记得"有两个任务在跑，
core 必须主动告诉她。

## 明确不做

- 人格模拟（情绪状态机、角色卡）。主动开口不是人格：它是 idle 里一次受频率上限约束的 `say`。
- 固定间隔轮询。唤醒只有两类：外部事件，和受预算约束的自唤醒定时器。
- 自建 agent 框架与工具协议：harness 干活，MCP 给外部能力，ACP 传话。
- 多用户、多租户、权限模型。这是单人自用工具。
